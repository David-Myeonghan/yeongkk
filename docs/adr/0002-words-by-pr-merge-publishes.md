# 0002 단어는 PR로만 들어오고, 합치는 순간이 게시다

> 결론: 단어는 git 파일 하나(`words/<로케일>/<id>.json`)이고, 넣는 길은 PR 하나다. 사람 · 자동 수집 · 제보 어느 입구든 같은 검사를 거친다.
> 검사 문지기는 돈다. 하지만 이 길로 합쳐진 단어는 아직 0개이고, 합치면 게시하는 배포(PR #12, 합침 2026-11-24)는 main에서 네 번 돌아 모두 D1 자리 표시 값 검사에서 멈췄다. 성공한 배포는 아직 없다.

상태: 채택 · 정한 날 2026-11-19 · 사후 기록(2026-11-24, AI가 씀. David 확인 전) · 확신: 중간

## 배경

단어를 넣는 입구가 셋이다. 사람이 직접 쓰는 것, 자동 수집이 올리는 것, 이용자 제보다.
입구마다 검사 방법이 다르면 구멍이 생긴다.
금칙어 · 중복 · 출처 · 개인정보는 한 곳에서 같은 기준으로 걸러야 한다.

## 결정 기준

- 입구가 여럿이어도 검사가 한 곳인가. (결정 기록 11-19 줄에 적힌 이유)
- 그 밖의 기준: David가 적는다

## 후보

1. 관리 화면 + DB. 버렸다. 이 후보를 버린 이유를 따로 적은 기록은 없다. 결정 기록은 고른 쪽의 이유(검사를 한 곳에서)만 적는다. 버린 이유: David가 적는다
2. 단어를 git의 파일로 두고 PR로만 넣는다. 합치는 순간이 게시다. 골랐다.

## 결정

2번.

- 단어 하나가 파일 하나다. 형식은 `schema/word.schema.json`이 정한다.
- PR이 올라오면 검사 8개를 돌린다. 형식 · 중복 · 출처 · 금지어 · 퀴즈 성립 · 개인정보 · 변경 범위 · 묶기다. 규칙은 `registry/checks.ts`가 기준이다.
- 자동 수집이 올린 PR(`auto/` 브랜치)은 단어 파일만 바꿀 수 있다.
- 합치기가 곧 게시다. 게시 단계(`deploy.yml`)는 PR #12로 합침(2026-11-24)이다. main에서 네 번 돌았고 네 번 모두 「DB 가 만들어졌는지 확인」 단계에서 멈췄다(`api/wrangler.jsonc`의 `database_id`가 자리 표시 값). 성공한 배포는 아직 없다.

## 결과

좋음

- 입구가 셋이어도 검사는 한 곳이다. 이유가 PR 댓글로 온다.
- 단어를 빼거나 고친 기록이 git 이력에 남는다.
- 단어 판이 파일이라 서버와 DB 없이 정적 파일로 나간다.

나쁨 (잃는 것)

- 단어 하나를 넣을 때마다 PR 한 번이다. 관리 화면보다 번거롭다.
- 알고 미룬 구멍이 있다. 두 PR이 서로 모르게 같은 말을 넣을 수 있다. 봇 PR을 브랜치 이름(`auto/`)으로만 구별한다. 띄어 쓴 금칙어(`시 발`)는 못 잡는다. 이유와 미룬 사정은 PR #1의 마지막 댓글에 있다.
- 설정 파일(`config/`)만 고친 PR은 이 문지기가 보지 않는다. 설정 검사는 `npm test`가 한다.
- 합치기가 곧 게시이므로, 잘못 합친 단어는 바로 나간다.

## 확인 방법

- 검사 규칙: `registry/checks.test.ts`, `registry/validate.test.ts`, `registry/build.test.ts`, `registry/add-word.test.ts`
- PR마다 도는 문지기: `.github/workflows/check.yml`. 저장소 규칙(ruleset)이 상태 검사 `test`와 `registry` 통과를 요구한다.
- 합치면 게시되는지: 아직 없음. 배포가 main에서 네 번 돌았지만 모두 D1 자리 표시 값 검사에서 멈췄다.

## 다시 볼 조건

- 자동 병합을 켤 때. 봇 판별을 브랜치 이름에만 맡기지 않고 「같은 저장소 + `auto/` + main 기준 범위 검사 통과」를 함께 요구하기로 PR #1에서 미뤄 두었다.
- 문지기가 PR의 `config/`도 보게 할지. (`docs/decisions.md` 「아직 안 정한 것」)
