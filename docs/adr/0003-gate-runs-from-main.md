# 0003 검사 문지기는 언제나 main의 것을 쓴다

> 결론: 단어 검사는 `pull_request_target`으로 돌려서, 워크플로 · 검사기 · 금칙어를 언제나 main 것으로 쓴다. PR에서는 `words/` 데이터만 가져온다.
> 처음 구현은 PR이 자기 검사기를 고쳐 통과할 수 있었다. 독립 리뷰가 찾았고, 일부러 깨뜨린 PR #4로 막힌다는 것을 확인했다.

상태: 채택 · 정한 날 2026-11-19 · 사후 기록(2026-11-24, AI가 씀. David 확인 전) · 확신: 높음

## 배경

PR이 올라오면 검사를 돌려 실패하면 합치지 못하게 한다.
그런데 검사기 코드도 같은 저장소에 있다. PR이 검사기를 같이 고치면, 고친 검사기가 그 PR을 검사한다.
검사하는 쪽이 검사받는 쪽의 손에 있으면 검사가 아니다.

## 결정 기준

- PR이 검사 기준을 바꿔서 통과할 수 있는가.
- PR의 코드가 쓰기 토큰을 가진 채 실행되는가.
- 그 밖의 기준: David가 적는다

## 후보

1. `pull_request`로 돌려 PR이 가져온 워크플로와 검사기를 그대로 실행한다. 버렸다. PR이 `checkScope`를 `return []`로 바꾸거나 `check` 스크립트를 `true`로 바꾸면 초록으로 통과한다. 승인이 0명이라 그대로 합칠 수 있다. 독립 리뷰의 Critical이었다.
2. `pull_request_target`으로 돌려 main을 받아 오고, PR의 `words/`만 `git archive`로 덮어쓴다. 심볼릭 링크는 거절한다. 골랐다.

## 결정

2번. 단어 검사 문지기(`.github/workflows/check.yml`)는 main의 워크플로 · 검사기 · 금칙어를 쓴다.
PR의 코드(`package.json` · `registry/` · 스크립트)는 이 워크플로에서 실행하지 않는다.
PR의 코드를 돌리는 테스트는 읽기 권한만 가진 다른 워크플로(`test.yml`)로 나눴다.

## 결과

좋음

- PR이 검사 기준을 고쳐서 통과할 수 없다. 검사기를 고친 PR(#4)이 main의 검사기에 막혔다.
- PR의 코드가 쓰기 토큰과 함께 실행되지 않는다.

나쁨 (잃는 것)

- 문지기는 `words/`만 본다. PR이 고친 검사기가 옳은지는 문지기가 보지 않는다. 그 PR의 `test.yml`이 본다.
- 사람이 올린 PR은 범위 제한이 없다. 사람이 검사기를 고치는 것은 막지 않고, 합쳐진 뒤부터 새 검사기가 문지기가 된다. (`registry/checks.test.ts`의 「사람 PR 은 범위 제한 없음」)
- `config/`만 고친 PR은 문지기가 보지 않는다. 틀린 설정이 합쳐질 수 있다. `npm test`가 실제 설정 파일을 전부 검사해서 PR마다 막는다. 문지기가 설정도 가져오게 할지는 정하지 않았다.
- 워크플로 파일을 고치는 일이 어려워졌다. main에 들어간 뒤에야 효과가 난다.

## 확인 방법

- 사람이 일부러 깨뜨린 PR #4(검사기를 고치고 출처가 하나뿐인 단어를 넣음, 합치지 않고 닫음). 상태 검사 `registry`가 실패했고 「출처」와 「변경 범위」 이유가 댓글로 달렸다. PR이 고친 검사기는 출처 검사를 꺼 둔 것이라, 「출처」 실패는 main의 검사기가 돌았다는 증거다. 이 PR의 브랜치 이름이 `auto/`라서 「변경 범위」도 같이 걸렸다.
- 저장소 규칙(ruleset)이 상태 검사 `registry`와 `test` 통과를 요구한다.
- 봇 PR의 변경 범위 규칙: `registry/checks.test.ts`
- 워크플로 파일 자체를 시험하는 자동 테스트: 아직 없음. 확인은 PR #4 한 번이다.
