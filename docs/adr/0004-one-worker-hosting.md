# 0004 웹 파일과 서버를 Cloudflare Worker 하나에 둔다

> 결론: 호스팅은 Cloudflare, 모양은 Worker 하나다. 웹 파일과 `/api/*`와 D1(DB)이 한 배포에 있고 주소도 하나다.
> 배포(PR #12)는 합쳐지지 않았고 한 번도 돌려 본 적이 없다. 로컬 Worker와 로컬 D1로만 확인했다.

상태: 채택 · 정한 날 2026-11-22(같은 날 저녁에 「Pages + 따로 둔 Worker」에서 지금 모양으로 바꿈) · 사후 기록(2026-11-24, AI가 씀. David 확인 전) · 확신: 중간

## 배경

필요한 것은 정적 웹 파일 호스팅, 이벤트와 제보를 받는 서버, 그 데이터를 넣을 DB다.
단어를 합칠 때마다 배포하고, 광고를 붙이고, 이용자가 없는 조용한 주에도 멈추지 않아야 한다.
일주일 일정 안에서 혼자 만들고 운영한다.

## 결정 기준

- 광고를 붙여도 되는가(무료 약관에 상업 이용 금지가 없는가).
- 합칠 때마다 배포해도 한도에 안 걸리는가.
- 조용한 주에도 멈추지 않는가.
- 배포 단계가 몇 개인가.

## 후보

(요금 · 한도는 2026-11-22에 공식 문서로 확인한 값이다. 바뀔 수 있다.)

1. Pages(웹 파일) + 따로 둔 Worker(서버). 버렸다. 배포가 두 번이고 주소가 둘이라 CORS(다른 출처 호출 허용)를 설정해야 한다. 대시보드가 Pages를 「레거시 Pages 워크플로」로 밀어 두었고 공식 문서가 새 프로젝트에 Workers 정적 자산을 권한다.
2. Worker 하나(정적 파일 + API + D1). 골랐다.
3. Vercel. 버렸다. 무료(Hobby)는 비상업 개인용만이다. 광고가 붙는다.
4. Firebase Hosting. 버렸다. 서버가 없다. 전송 하루 360MB(가격 페이지 기준)를 넘으면 그 달 남은 기간 꺼진다.
5. Netlify. 버렸다. 월 300 크레딧에 프로덕션 배포 1회가 15크레딧이다. 배포 20회면 다음 달까지 멈춘다. 단어 PR을 합칠 때마다 배포한다.
6. GitHub Pages. 버렸다. 이벤트 · 제보를 받을 서버가 없다.
7. AWS(S3 + CloudFront + Lambda + DynamoDB). 버렸다. 서비스 넷을 엮고 권한을 잡는 시간이 일주일 일정에 안 맞는다.
8. Supabase. 보류했다. 호스팅이 아니다. 1주 동안 요청이 없으면 멈춘다. DB만 옮길 때의 대안으로 둔다.

## 결정

2번. 호스팅은 Cloudflare다.

- `api/wrangler.jsonc`의 `assets`가 `web/dist`를 서빙한다. `/api/*`만 코드가 먼저 받고(`run_worker_first`), 나머지는 파일로 답한다.
- 서버 경로는 전부 `/api/` 아래이고 웹과 같은 출처다. 웹이 다른 출처를 부르지 않으니 서버에 CORS 응답이 없다.
- 설정 파일의 `api` 값은 `/`로 시작하는 상대 경로만 받는다. 검사기(`schema/config.schema.json`)가 막는다. 웹 쪽 읽기(`web/src/data/guards.ts`)는 아직 `https://` 주소도 받는다. 설정이 검사를 거쳐 들어오므로 지금은 문제가 되지 않지만, 두 곳이 같지 않다.
- DB는 서버의 `api/src/db.ts` 한 곳에서만 부른다.
- 빌드는 GitHub Actions가 하고 `wrangler deploy`로 올린다. Cloudflare 쪽 빌드 횟수 한도를 쓰지 않는다.

## 결과

좋음

- 배포 1번, 주소 1개, 토큰 권한 1종(Workers Admin + D1).
- 정적 파일 요청은 무료이고 무제한이다. 코드가 받는 요청(`/api/*`)만 하루 10만 건(Workers 무료)을 센다.
- 호스팅 · 서버 · DB가 한 계정이다. 무료에 기간 제한이 없다.
- 나갈 길이 있다. 정적 파일은 어디로든 옮겨지고, DB 호출이 한 파일에 모여 있다.

나쁨 (잃는 것)

- Pages의 PR별 미리 보기 주소를 잃었다. 웹 변경을 합치기 전에 공개 주소로 볼 수 없다.
- D1 쓰기가 하루 10만 행이다. `events` 표는 색인이 둘이라 이벤트 1건이 3행이다. 한 판에 이벤트 15개라고 가정하면 하루 약 2,200판이 한계다. 넘으면 그날 쓰기가 막히고, 이벤트는 다음에 다시 보낸다. 쓰기 한도를 서버가 스스로 세는 코드는 없다.
- 서버를 다른 주소로 옮기려면 서버에 CORS를 넣고 설정 스키마를 같이 고쳐야 한다.
- 무료는 지원과 가용성 약속이 없다. 결제(카드 정보 수집)를 붙이는 날에는 유료 플랜이 필요하다.
- 아직 배포한 적이 없다. D1 `database_id`는 자리 표시 값이고, 계정 가입과 토큰 권한이 실제 배포에서 충분한지는 모른다.

## 확인 방법

- `api/src/index.test.ts`: `/api/`가 아닌 요청은 파일(ASSETS)로 넘기고, 다른 출처의 POST는 403이다.
- `registry/config.test.ts`: 설정의 `api`가 `/`로 시작하는 경로만 받는지(`https://…`, `//x`, `/\x`는 거절).
- `web/src/data/guards.test.ts`: 웹 쪽 읽기. 여기서는 `https://example.com/api`를 받아들인다.
- 실제 배포와 D1: 아직 없음. 로컬 Worker + 로컬 D1에서 한 판이 끝까지 돈 것을 2026-11-24에 손으로 확인했다(계획 문서의 실측 기록).

## 다시 볼 조건

- 이벤트가 하루 약 2,200판 분량을 넘을 때(D1 쓰기 한도).
- 서버를 다른 주소로 옮길 때(CORS와 설정 스키마).
- 결제를 붙일 때(유료 플랜).
- DB만 바꿀 때(보류한 Supabase를 다시 비교).
