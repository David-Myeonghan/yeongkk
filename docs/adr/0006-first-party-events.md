# 0006 이벤트는 직접 받는다 (Firebase를 쓰지 않는다)

> 결론: 이용 이벤트를 우리 서버(`POST /api/events`)가 받아 D1에 원본 그대로 적는다. 저장하는 칸을 우리가 정한다.
> 실험을 변형별로 세려면 원본 이벤트가 필요해서다. 대신 쓰기 한도와 통계 화면을 직접 책임진다.

상태: 채택 · 정한 날 2026-11-22 · 사후 기록(2026-11-24, AI가 씀. David 확인 전) · 확신: 중간

## 배경

공개 뒤 2주 동안 세 숫자를 본다. 연 사람, 완주, 공유다(`docs/prd.md`).
「웃긴 오답」 실험은 변형(`on` / `off`)마다 완주율과 공유율을 따로 세야 한다.
로그인이 없고 이메일 · 전화번호 · 아이디 · IP를 저장하지 않는다는 제약이 있다.

## 결정 기준

- 실험을 변형별로 셀 수 있는가.
- 저장하는 칸을 우리가 정할 수 있는가.
- 그 밖의 기준: David가 적는다

## 후보

1. Firebase Analytics. 버렸다. 결정 기록의 이유는 이것뿐이다. 실험을 변형별로 세려면 원본 이벤트가 필요하고, 저장하는 칸을 직접 정하고 싶다. Firebase의 한도나 요금을 비교한 기록은 없다.
2. 직접 받는다. 서버 경로 + D1. 골랐다.

## 결정

2번.

- 웹이 이벤트를 모아 `{api}/events`로 보낸다. 서버는 모르는 이름과 나쁜 속성을 걸러 저장한다.
- 이벤트 이름 목록은 한 파일(`quiz-core/events.ts`)에 두고 웹과 서버가 같이 쓴다. 한쪽만 고치면 서버가 그 이벤트를 조용히 버리기 때문이다.
- 이벤트의 날짜는 서버가 받은 시각의 한국 날짜(UTC+9)다. 기기 시계는 틀릴 수 있어서다.
- 이벤트를 보내다 실패해도 퀴즈는 멈추지 않는다. 실패한 이벤트는 남겨 두었다가 다음에 보낸다.
- 숫자는 `GET /api/stats` 하나로 읽는다. 날짜별 단계별 사람 수, 실험 변형별 수, 공유 경로별 수를 낸다.

## 결과

좋음

- 변형별 노출 · 완주 · 공유를 원본에서 센다. 공유는 끝까지 마친 것(`completed`)만 센다. 공유 창을 열었다 닫은 것은 시도로만 센다.
- 저장하는 칸이 정해져 있다. IP와 User-Agent는 저장하지 않는다.
- 이벤트 서버가 느리거나 죽어도 화면이 막히지 않는다.

나쁨 (잃는 것)

- 통계 화면이 없다. 숫자를 보려면 토큰을 넣어 `GET /api/stats`를 부르거나 D1을 직접 조회한다.
- D1 쓰기 하루 10만 행 한도를 직접 쓴다. 이벤트 1건이 3행이라 하루 약 2,200판이 한계다(0004). 서버에는 쓰기 한도를 세는 코드가 없다. 리뷰(2026-11-23)가 지적했고 고치지 않고 남겼다.
- 기기에서 만든 무작위 값으로 사람을 센다. 저장소를 지우고 다시 연 사람은 새 사람이다. 2주 전체의 겹치지 않는 사람 수는 내지 않는다.
- 날짜 경계가 한국 시간이다. 다른 나라 로케일을 넣으면 하루 경계가 어긋난다.
- 실제 D1에서 통계 쿼리가 색인을 타는지는 확인하지 못했다.

## 확인 방법

- 받는 쪽: `api/src/events.test.ts`(크기 한도, 속성 걸러내기, 날짜가 UTC+9인지, IP · User-Agent를 저장하지 않는지)
- 세는 쪽: `api/src/stats.test.ts`(같은 사람이 여러 번 열어도 1명, 실험 변형별 수, 취소한 공유는 공유로 세지 않음)
- 보내는 쪽: `web/src/telemetry/events.test.ts`, `web/src/telemetry/queue.test.ts`, `web/src/telemetry/send.test.ts`

- 실제 D1과 실제 기기: 사람. 아직 없음.
