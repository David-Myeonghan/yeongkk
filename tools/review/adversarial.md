# 반증 절차

목적은 놓치는 결함을 줄이는 것이다. 차단을 늘리는 것이 아니다.
기준 목록만 훑고 끝내지 않는다. 목록은 보이는 코드만 평가한다. 실제 결함은 대개 작성자가 쓰지 않은 길에 있다.

## 1단계 — 찾기

바뀐 곳 가운데 사용자 동작 · 상태 · 경계에 닿는 곳을 위험한 순서로 1~3곳 고른다.
곳마다 작성자가 본문 · diff · 테스트에서 다루지 않은, 가장 그럴듯한 실패를 하나 적는다.
모양은 「구체적인 입력 → 상태 → 눈에 보이는 증상」이다.

후보로 먼저 볼 입력: 빈 값과 경계 값, 두 번 누름과 다시 들어옴, 전에 저장된 옛 모양의 데이터, 권한 밖의 요청, 옛 버전과 새 버전이 같이 도는 동안.

동작에 닿는 변경이 없으면(문서, 이름 바꾸기, 설정) 후보는 0개다. 지어내지 않는다.

## 2단계 — 반증

1. 후보마다 묻는다. 「이 지적이 틀렸다면 무엇이 이미 막고 있는가.」 검색하고 읽어서 막는 코드 · 타입 · 테스트를 찾는다. 찾으면 버리거나 질문으로만 남긴다. 못 찾고 그 길이 닿을 수 있음을 한 줄로 보였을 때만 살린다. 확실하지 않으면 차단이 아니다.
2. 테스트를 본다. PR 이 막겠다는 동작의 소스 줄을 하나 고르고, 가장 그럴듯한 틀린 구현을 말로 심는다(비교 `>` 를 `>=` 로, 조건을 항상 참으로, 하나 차이, 부호). 어느 단언이 빨개지는지 짚는다. 짚지 못하면 「이 테스트는 그 틀린 구현을 통과시킨다」로 남긴다.
3. 버그를 고치는 PR 이면, 고친 줄을 머릿속으로 되돌렸을 때 어느 테스트가 빨개지는지 짚는다.
4. 승인으로 기울었으면 닫기 전에 「이 PR 이 실제로 깨진다면 가장 그럴듯한 한 가지」를 하나 더 구성해 닿을 수 있는지 본다.
5. 읽어서 결론이 안 나는 것만, 관련 테스트 파일 하나를 좁게 돌려 확인한다. 전체 테스트 · 빌드는 돌리지 않는다. 돌렸으면 명령과 결과를 근거로 적는다.

## 3단계 — 살아남은 것 다시 보기

살아남은 후보만, 가장 틀리기 쉬운 눈 하나로 다시 본다.

- 맞음: 분기, 하나 차이, 없는 값.
- 상태: 쓰는 곳이 둘인가, 순서가 뒤집히면 어떻게 되는가. 사용자에게 보이는 실패(값이 어긋남, 사라짐, 두 번 실행)만 차단 후보다.
- 경계: 인용 · 주입, 권한이 넓어지는가, 옛 버전과 같이 돌 때.
- 원인과 증상: 고쳤다는 PR 이 원인을 없앴는가, 증상 자리에 방어만 덧댔는가.

## 4단계 — 스스로 점검

- 차단으로 올린 지적마다 파일:줄과 실패 시나리오가 있는가.
- 본문의 판정 줄과 판정 파일의 값이 같은가.
- 추측으로 쓴 문장이 없는가.
