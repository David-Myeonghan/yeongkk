# 리뷰 기준

이 저장소의 PR 리뷰어가 따르는 기준이다. 리뷰어는 이 파일을 먼저 읽는다.

## 원칙 (Kent Beck 의 Simple Design)

1. 동작하는가.
2. 의도가 드러나는가.
3. 같은 지식이 두 번 적혀 있지 않은가.
4. 필요 없는 요소가 없는가.

## 먼저 읽을 것

`review-context/` 폴더에 리뷰 전에 만들어 둔 자료가 있다. 본문을 쓰기 전에 읽는다.

- `pr.md`: PR 제목과 본문. 작성자가 주장하는 것.
- `diff.patch`: `pr.md` 의 「비교 기준」부터 이 PR 끝까지의 변경. 쌓인 PR 을 `--base` 없이 돌렸으면 앞 PR 의 변경이 섞여 있다. 그때는 `pr.md` 에 적힌 PR 의 제목 · 본문이 말하는 범위만 판정한다.
- `changed-files.txt`: 바뀐 파일 목록과 줄 수.
- `diagnostics.md`: lint · 타입 검사 · 테스트를 이미 돌린 결과. **다시 돌리지 않는다.**
- `previous-review.md`: 증분 리뷰일 때만 있다. 지난 리뷰 본문.

그다음 저장소의 `README.md` 와 바뀐 폴더의 `README.md` 를 읽고, 바뀐 파일의 주변 코드를 읽는다.

## 집중할 곳

- **본문의 주장**: PR 본문이 「된다」고 적은 것이 코드에서 참인가. 주장마다 파일:줄이나 테스트 이름으로 확인한다.
- **재사용 · 중복**: diff 에 새 함수 · 타입 · 상수가 있으면 「의심될 때만」이 아니라 항상 같은 목적의 기존 구현을 검색한다. 결과를 본문에 한 줄로 남긴다(「새 선언 N건 대조 — 중복 없음 / 발견 M건」). 같은 diff 안에 같은 로직이 두 번 적힌 것도 본다.
- **계약 퉁치기**: 타입을 맞추려고 넣은 단언(`as`, `!`), 뜻 없는 기본값(`?? ""`), 삼킨 오류. 값을 만들 수 없으면 타입을 고치거나 앞에서 실패시키는 것이 맞다.
- **테스트의 질**: 구현을 틀리게 바꿔도 통과하는 테스트인가. 소스를 그대로 베낀 단언인가. 고친 버그를 다시 넣으면 빨개지는 테스트가 있는가.
- **경계**: 바깥에서 들어오는 값(요청 본문, 저장된 값, 받아 온 JSON, 주소)이 검사 없이 쓰이는 곳. 비밀값이 로그나 검토 안 된 코드에 닿는 길.
- **상태를 바꾸는 순서**: 같은 값을 쓰는 곳이 둘 이상인가. 부수 효과보다 먼저 상태를 적는가. 두 번 눌렀을 때, 도중에 꺼졌을 때.
- **개인정보**: 저장하거나 기기 밖으로 보내는 것이 본문에 적힌 것과 같은가.
- **지나친 설계**: 지금 필요 없는 추상화 · 옵션 · 한 줄짜리 래퍼.
- **읽는 사람**: 설명 없는 숫자, 하는 일과 다른 이름, 코드와 어긋난 주석 · 문서.

지적하지 않는 것: 취향, 서식, 「테스트를 더 쓰면 좋겠다」처럼 빠진 경우를 짚지 못한 말, 결과를 한 줄로 말할 수 없는 것.

## 판정

지적을 먼저 분류하고, 판정은 그 결과로 정한다. 결론을 먼저 깔고 지적을 거기에 맞추지 않는다.

- **갈래 A — 동작 결함**: 「이 입력 · 상태 → 이 틀린 결과」를 구성했고, 막는 것이 없음을 코드에서 보였다.
- **갈래 B — 입증된 품질 결함**: 동작은 같아도, 근거가 결정적(파일:줄)이고 고치는 방법이 분명하다. 대상은 넷이다. 입증된 중복, 계약 퉁치기, 틀린 안내문(없는 이름 · 경로를 가리키는 주석 · 오류 문구 · 문서), 구현이 틀려도 통과하는 테스트.
- **참고**: 질문, 제안, 따로 할 만한 크기의 일, 확인하지 못한 것.

A 나 B 가 하나라도 남으면 `REQUEST_CHANGES`, 없으면 `APPROVE`.

B 를 참고로 내릴 수 있는 사유는 둘뿐이다. 입증하지 못했다. 또는 고치는 일이 따로 할 만한 크기다. 내릴 때는 어느 쪽인지 적는다. 「고치는 것이 한 줄이라 사소하다」는 내리는 사유가 아니다. 고치기 쉬울수록 지금 고치는 것이 맞다.

참고로 남긴 지적은 합쳐진 뒤 거의 반영되지 않는다. 그래서 입증된 것은 차단으로 올린다.

판정을 내리기 전에 `review-context/adversarial.md` 를 한 번 읽고 그 절차를 따른다.
본문을 쓰기 전에 `review-context/output-rules.md` 를 읽는다.
